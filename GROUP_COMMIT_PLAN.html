Group GitHub Commit Plan

Smart Textile Business Management and AI-Powered E-Commerce Platform

**Team size:** 5 members **Purpose:** A practical commit plan for dividing implementation work, explaining each member's responsibilities, and maintaining a clear GitHub history.

---

1. Git Rules for the Whole Team

Branch naming

Each member should create a branch from `main` using this format:

feature/member-1-customer-frontend
feature/member-2-core-backend
feature/member-3-inventory-production
feature/member-4-ai-analytics
feature/member-5-admin-qa-devops

Commit message format

Use short, action-oriented commit messages:

feat(scope): add product catalogue filters
fix(scope): prevent duplicate payment webhook processing
test(scope): add concurrent stock reservation tests
docs(scope): document deployment and API setup
chore(scope): configure CI workflow

Commit guidelines

  • One commit should represent one logical change.
  • Do not combine unrelated frontend, backend and documentation changes in one commit.
  • Do not commit passwords, API keys, `.env` files or payment secrets.
  • Run the relevant tests before opening a pull request.
  • Pull requests should explain what changed, how it was tested and which member owns the work.
  • Every member reviews at least one other member's pull request.
  • The final merge to `main` should be performed only after integration tests pass.

    • ---

    2. Recommended Implementation Order

    The commits should generally be merged in this order:

  • Shared project setup and database foundation.
  • Authentication and role-based access control.
  • Product catalogue and customer storefront.
  • Admin product management.
  • Cart, checkout and server-side order validation.
  • Inventory reservation and movement ledger.
  • Payment methods and PayHere webhook handling.
  • Production workflow and worker portal.
  • AI assistants, forecasting and analytics.
  • Automated testing, security review, deployment and final documentation.

    • Some commits can be developed in parallel, but database schema and API contracts must be agreed before dependent work is merged.

    Commit 1.1: Create the customer application shell

    Commit message:

    feat(customer-ui): create storefront layout and navigation

    Work included

  • Create the main customer layout.
  • Add header, logo, navigation links and footer.
  • Add responsive navigation for mobile devices.
  • Add loading, empty and error states.
  • Add the customer route structure.
  • Add a shared design style for buttons, forms, alerts and product cards.

    • Why this is needed

    The application needs a consistent customer experience before individual pages are added. A shared layout prevents every page from implementing its own navigation and visual rules.

    Expected result

    A user can open the customer application, navigate between the home page, catalogue, login, cart and orders pages, and see a consistent responsive layout.

    Commit 2.4: Implement order creation and status transitions

    Commit message:

    feat(orders): add validated checkout and order lifecycle

    Work included

  • Accept cart data from the frontend.
  • Re-fetch products from the database.
  • Recalculate prices and totals on the server.
  • Validate measurements and addresses.
  • Create orders and order items inside a database transaction.
  • Implement valid order status transitions.
  • Add order status history.
  • Prevent customers from viewing other customers' orders.
  • Return line-level conflicts for changed prices or unavailable stock.

    • Why this is needed

    The browser cannot be trusted for prices, totals or ownership. Server-side order validation protects business rules and prevents incorrect orders.

    Expected result

    A valid checkout creates a correctly calculated order, while invalid or stale cart data produces a useful response for the frontend.

    ---

    Commit 2.5: Implement payment methods and PayHere webhooks

    Commit message:

    feat(payments): add COD bank transfer and idempotent PayHere webhooks

    Work included

  • Add payment records and payment status transitions.
  • Support COD order confirmation.
  • Support bank-transfer slip submission or verification flow.
  • Create PayHere checkout data.
  • Verify webhook signatures.
  • Verify webhook amount against the order total.
  • Store raw webhook payloads and processing results.
  • Prevent duplicate webhook processing.
  • Confirm the order only after a valid server-to-server event.

    • Why this is needed

    Payments affect order confirmation and stock deduction. Webhook processing must be idempotent because gateways may send the same event multiple times.

    Expected result

    The system supports multiple payment methods without confirming unpaid or tampered orders.

    Member 3: Inventory and Production Developer

    **Primary area:** `backend/src/inventory`, `backend/src/production`, worker functionality **Branch:** `feature/member-3-inventory-production`

    Commit 3.1: Implement single-source inventory model

    Commit message:

    feat(inventory): add inventory quantities and movement ledger

    Work included

  • Use the inventory table as the source of truth for stock.
  • Store available, reserved and minimum quantities.
  • Add inventory movement records.
  • Support receiving stock and adjusting stock.
  • Record the user and reason for manual changes.
  • Add inventory history endpoints.
  • Add low-stock query support.

    • Why this is needed

    Keeping stock in multiple tables causes inconsistency. The inventory table and movement ledger provide traceability for every stock change.

    Expected result

    Administrators can view current stock and see exactly why the quantity changed.

    ---

    Commit 3.2: Implement reservation, deduction and release logic

    Commit message:

    feat(inventory): add transaction-safe stock reservation lifecycle

    Work included

  • Reserve stock when an order is created.
  • Reject orders when available stock is insufficient.
  • Deduct stock after payment confirmation or COD confirmation.
  • Release reservations after cancellation or payment failure.
  • Use database transactions and row locking.
  • Add movement records for reserve, sale and release operations.
  • Ensure stock cannot become negative.

    • Why this is needed

    Two customers may try to buy the same item at the same time. Database locking and transactions prevent overselling.

    Expected result

    Stock remains correct even when multiple checkout requests happen concurrently.

    ---

    Commit 3.3: Implement production task generation

    Commit message:

    feat(production): create production tasks from confirmed orders

    Work included

  • Generate tasks only for custom, uniform or measurement-based products.
  • Assign the initial Cutting stage.
  • Store order item and task relationships.
  • Track task status and production stage.
  • Add task notes and due dates where supported.
  • Skip production for retail-only products.

    • Why this is needed

    The factory workflow must begin automatically after an order is confirmed. Retail fabric orders should not create unnecessary production tasks.

    Expected result

    Confirmed custom orders appear in the production workflow with the correct tasks.

    Commit 3.4: Implement worker task workflow

    Commit message:

    feat(worker): add production task portal and stage transitions

    Work included

  • Allow workers to view tasks assigned to their stage.
  • Support Pending, In Progress and Done task statuses.
  • Support movement through Cutting, Stitching, Finishing and Quality Check.

  • Prevent workers from changing tasks outside their permitted stage.

    • Why this is needed

    Workers need a simple interface that reflects the physical factory process while preserving accountability.

    Expected result

    Workers can update assigned tasks and administrators can see real-time production progress.

    3. Final Integration Commits

    These commits should be created only after all feature branches have been reviewed.

    Integration commit 1: Connect all services

    chore(integration): connect frontend backend and AI service

    Confirm that:

  • The frontend reaches the backend API.
  • The backend reaches PostgreSQL.
  • The backend reaches the AI service.
  • Docker Compose starts all required containers.
  • Environment variables are documented.

    • Integration commit 2: Fix cross-module issues

    fix(integration): resolve cross-module API and workflow issues

    Check:

  • Product IDs and order IDs use the same format everywhere.
  • Order and payment statuses match across frontend and backend.
  • Inventory is updated at the correct order/payment events.
  • Production tasks are created only when required.
  • Admin and worker permissions are enforced.

    • Integration commit 3: Release preparation

    chore(release): prepare final tested project release

    Confirm:

  • All tests pass.
  • No secrets are committed.
  • Database migrations work from a clean database.
  • Docker images build successfully.
  • Documentation matches the current code.
  • The final demo workflow works from login to delivery.

    4. Pull Request Checklist

    Every member should use this checklist before requesting a merge:

  • [ ] My branch contains only related work.
  • [ ] The commit messages explain the changes clearly.
  • [ ] The code follows the existing project structure.
  • [ ] Validation and error handling are included.
  • [ ] Tests were added or updated.
  • [ ] I tested the feature locally.
  • [ ] I did not commit `.env` files or secrets.
  • [ ] API or database changes are documented.
  • [ ] At least one other member reviewed the pull request.
  • [ ] CI checks pass.

    • ---

    5. Contribution Evidence for the Final Report

    Each member should keep the following evidence for the project report and presentation:

  • GitHub branch name.
  • List of commits authored by the member.
  • Pull requests created and reviewed.
  • Screenshots of completed features.
  • Tests written and test results.
  • Problems encountered and how they were solved.
  • Short explanation of the member's technical contribution.

    • The contribution should be evaluated by the quality and importance of the work, not only by the number of commits. A single well-designed database transaction or security feature may be more valuable than many small visual commits.
